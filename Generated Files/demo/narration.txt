Windows on Arm video editors need a native OpenShot release path, but the verified demand evidence is deliberately modest: one open upstream issue, OpenShot issue 5853. We have no approved download or user count, so we do not claim one. The current production chain serves x64 and x86, and the Arm gap crosses three repositories.
Before this project, there was no production Arm64 artifact edge from OpenShotAudio, through libopenshot and its Python binding, into the OpenShot application, Inno installer, or MSIX package. The readiness review found no candidate executable, DLL, PYD, wheel, or MSIX in the three assessed repositories.
The project used a manager and specialist workers to turn that gap into an evidence-backed, documentation-only release plan. Design, independent risk review, implementation review, and Arm readiness stayed separated. Product code stayed untouched, and every claim had to survive a named gate.
The approved design replaces duplicated architecture assumptions with one reusable contract: windows-arm64-clangarm64-v1. A signed, checksummed dependency lock ties the compiler, Python, Qt, native libraries, licenses, producer artifacts, and payload hashes to one digest. Mutable or foreign inputs stop the lane.
Delivery is split into separate upstream changes. PR A produces OpenShotAudio. PR B consumes that exact artifact and produces libopenshot plus the Python binding. PR C consumes PR B, freezes OpenShot, and creates Inno and MSIX candidates. Consumers cannot fall back to a branch or merge before their producer contract is accepted.
Correctness has a reusable oracle, not a visual guess. Its standard-library generator defines 60 frames at 64 by 36, plus 96,000 stereo audio frames, and checks fixed video, audio, and manifest hashes before product code runs. The 60 ordered frame hashes and manifest digest were mechanically reproduced, but the real native writer was not run.
The executable runbook then carries that contract through gates G0 to G13: baseline freeze, toolchain lock, recursive Arm64 PE and import closure, Qt and QWidget probes, deterministic rendering, packaging, signing, migration, cleanup, and two physical device classes. Every command records raw evidence, and producer failure blocks every consumer.
What works today is the evidence framework. Three release-detail tests passed, and the documentation oracle reproduced its manifest hash. The broader host suite ran 52 tests with 25 errors dominated by missing Qt and openshot modules. Those are AMD64 host results, not native Arm64 application success.
The current verdict is NOT READY because no native Arm64 candidate exists and the required G0 and G1 infrastructure is not provisioned. The architecture oracle is now corrected: UNKNOWN process machine plus ARM64 native machine means native execution; any nonzero process-machine value means WOW or emulation.
The next gates are release-owner baseline approval, a signed toolchain lock, a native GitLab runner, and implementation of the three upstream PRs. Native import, render, package, performance, power, and hardware claims remain unmade until owner-produced evidence passes the runbook.
